Section A — Multiple Choice Questions

Q1. What does copy.deepcopy(global_model) at server.py:114 prevent?

  1. It prevents the client from using GPU memory
  2. It prevents clients from accidentally modifying the server's global model during local training
  3. It copies the model to a different device
  4. It prevents gradient accumulation
Show Answer
b) Without deepcopy, all clients share a reference to the same model object. Any parameter update by one client would instantly affect others, breaking the independence assumption of FedAvg.

Q2. After three MaxPool2d(2) layers applied to 28×28 input, the spatial size is:

  1. 4×4
  2. 3×3
  3. 2×2
  4. 7×7
Show Answer
b) 3×3. MaxPool2d(2) divides each dimension by 2 (floor): 28 → 14 → 7 → floor(7/2)=3. This is why Linear(128×3×3=1152, 128) is correct.

Q3. Why does FedAvg weight client contributions by sample count?

  1. To give more power to richer clients
  2. Because clients with more data computed more gradient steps
  3. Because unweighted averaging over-represents small clients and under-represents large ones, biasing the global model
  4. To ensure equal communication cost
Show Answer
c) With unweighted averaging, a client with 10 samples gets the same vote as one with 10,000. Sample-size weighting ensures the global model reflects the empirical distribution across all data.

Q4. Which statement about the validation set in your code is true?

  1. It is partitioned among clients with the same strategy as training data
  2. It is split 50/50 between clients
  3. It remains centralised and is never partitioned — all evaluation is on the global val_loader
  4. Each client evaluates on its own subset of the validation set
Show Answer
c) val_loader is created from the full MedMNIST val split in pathmnist_loader.py and passed directly to run_federated_training() without partitioning. This gives an unbiased global performance estimate. ✓

Q5. What is wrong with the smoke test in main.py lines 76–83?

  1. It uses too many GPU resources
  2. The lambda returns all ~90k labels instead of the 64-sample subset, so FL trains on the full dataset
  3. It doesn't save checkpoints
  4. It uses the wrong model architecture
Show Answer
b) subset_factory.get_labels = lambda: train_subset_labels where train_subset_labels contains all ~90k labels. partition_dataset receives all labels and partitions the full training set, defeating the purpose of the smoke test.

Section B — FedAvg Calculation Problems

Problem 1 — Manual FedAvg

Three clients participate in round 1. After local training:

  • Client A: w = 2.0, n = 50 samples
  • Client B: w = 6.0, n = 150 samples
  • Client C: w = 4.0, n = 100 samples

Compute the FedAvg global weight.

Show Solution
N = 50 + 150 + 100 = 300 w_global = (50/300)×2.0 + (150/300)×6.0 + (100/300)×4.0 = 0.1667×2.0 + 0.5×6.0 + 0.3333×4.0 = 0.333 + 3.000 + 1.333 = 4.667

Verify:

import torch
from federated_learning.federated.aggregation import fedavg_aggregate
result = fedavg_aggregate(
    [{'w': torch.tensor([2.0])},
     {'w': torch.tensor([6.0])},
     {'w': torch.tensor([4.0])}],
    [50, 150, 100]
)
print(result['w'])  # tensor([4.6667])

Problem 2 — Communication Cost

Compute total bytes for 20 rounds, 5 clients (all participating), PathMNISTCNN (241,993 params), float32.

Show Solution
bytes_per_round = 5 clients × 241,993 params × 4 bytes × 2 directions = 9,679,720 bytes ≈ 9.2 MB per round total = 20 × 9.2 = 184 MB

For comparison: PathMNIST training data ≈ 90k × 28×28×3 ≈ 212 MB. FL transfers similar bandwidth but never exposes raw images.

Problem 3 — Client Drift

A client starts with global weight w_g = 1.0. Local gradient is constant ∂L/∂w = −2.0. SGD lr=0.1.

a) Weight after E=1 step?  b) After E=5 steps?  c) A second client has constant gradient +2.0. With equal n, what is FedAvg after E=5?

Show Solution
a) w = 1.0 − 0.1×(−2.0) = 1.2 b) w = 1.0 + 5×0.2 = 2.0 c) Client 2: w = 1.0 − 5×0.2 = 0.0 FedAvg: (2.0 + 0.0) / 2 = 1.0 (back to start!)

This illustrates client drift: clients with opposing gradients cancel each other after averaging, making no net progress despite local training. This is why non-IID + high E is damaging.

Debug 1 — Find the bug

    device = torch.device(device)
    model.train()   # ← student changed this line
    criterion = criterion or torch.nn.CrossEntropyLoss()

Show Answer
model.train() enables Dropout (randomly zeroes neurons) and BatchNorm training mode. Evaluation results become non-deterministic — the same input gives different outputs each pass. Also, without torch.no_grad(), gradients are computed unnecessarily, wasting memory. Fix: model.eval() + with torch.no_grad():.

Debug 2 — What is wrong?

global_state = fedavg_aggregate(
    updated_states,
    sample_counts=[1] * len(updated_states)   # ← bug here
)
Show Answer
Using [1,1,1,...] gives every client equal weight regardless of actual sample count. This is unweighted averaging, not FedAvg. With unequal client data sizes, small clients will disproportionately influence the global model. Pass the real sample_counts list.

Debug 3 — Why are these results misleading?

# Experiment A: Federated IID, 20 rounds, 2 local_epochs
#   → reports 80% validation accuracy
# Experiment B: Centralized baseline
#   → epochs = max(1, config.local_epochs) = 2 epochs
#   → reports 65% validation accuracy
# Conclusion: "FL outperforms centralized by 15%!"
Show Answer
The federated model trains for 20 rounds × 2 epochs = 40 equivalent data passes. The centralized baseline trains for only 2 epochs. The comparison is completely invalid — of course 40 epochs beats 2. For a fair comparison, centralized should train for rounds × local_epochs = 40 epochs (Bug #4, main.py:44).
