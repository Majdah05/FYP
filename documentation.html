Federated Learning Framework Documentation

This project implements a reproducible and modular federated learning baseline in Python using PyTorch. The goal is to provide a clean research-friendly foundation for Federated Averaging (FedAvg), centralized model comparison, and future integration of more advanced security and privacy mechanisms.

The current implementation focuses on the baseline: a clean FedAvg simulation, configurable experiments, centralized PathMNIST training, and a dataset-independent interface for future IDS work.

1. Project purpose

The project is designed for a university Final Year Project and supports:

  • Centralized training on PathMNIST as a benchmark baseline
  • Federated training using FedAvg
  • IID and non-IID client partitioning
  • Configurable experiments through command-line arguments and YAML files
  • Evaluation on validation/test metrics
  • A modular structure to later add IDS datasets, secure aggregation, differential privacy, and robustness techniques

2. Why this project is structured this way

The code is separated into independent modules so each component can be understood and extended without rewriting the whole framework. This is important for research because the training algorithm, data partitioning, model architecture, metrics, and logging are all clearly separated.

Module Role
main.py Main entry point for starting a full experiment
federated_learning/config.py Runtime configuration parsing and validation
federated_learning/datasets/ Loading datasets and partitioning data into simulated clients
federated_learning/models/ Model definitions such as CNN and MLP
federated_learning/federated/ Client logic, server logic, and FedAvg aggregation
federated_learning/training/ Centralized baseline and model evaluation
federated_learning/utils/ Logging, metrics saving, and plotting functions

3. Configuration system

Important settings are not hardcoded in the training logic. They are accepted at runtime via command-line arguments or YAML configuration files. This makes experiments reproducible and easy to compare. 

python main.py --dataset pathmnist --num_clients 5 --rounds 20 --local_epochs 2 --batch_size 64 --lr 0.01 --distribution iid

Example YAML configuration:

dataset: pathmnist
num_clients: 5
rounds: 20
local_epochs: 2
batch_size: 64
lr: 0.01
optimizer: sgd
distribution: iid
client_fraction: 1.0
seed: 42
output_dir: results

The configuration is validated in ExperimentConfig.validate(). Invalid settings such as a non-positive learning rate, unsupported dataset, or invalid optimizer produce clear errors instead of running silently.

4. Centralized PathMNIST baseline

The centralized training pipeline acts as a reference model. It trains a CNN on the official PathMNIST training split and evaluates it on a validation and test split. This allows the research project to compare a classical centralized model with a federated model trained across many clients. 

python main.py --dataset pathmnist --num_clients 5 --rounds 5 --local_epochs 2 --batch_size 64 --lr 0.01 --distribution iid --model cnn

Key behavior:

  • Downloads PathMNIST using the official MedMNIST package
  • Uses training, validation, and test splits
  • Trains a CNN on 28×28 RGB inputs
  • Reports validation metrics
  • Stores history and final metrics

6. Data partitioning

Only the training set is partitioned among clients. Validation and test data remain central and untouched to avoid leakage.

IID partitioning

The IID strategy randomly shuffles all training indices and splits them across clients. This creates client datasets with similar class counts and similar sample sizes.

Non-IID partitioning

The non-IID strategy uses a Dirichlet distribution to create label-skewed client data. The dirichlet_alpha parameter controls heterogeneity:

  • Higher alpha → more uniform label distributions
  • Lower alpha → more heterogeneous distributions
proportions = rng.dirichlet(np.full(num_clients, dirichlet_alpha))

Every sample is assigned to exactly one client, and the framework checks that no client is empty when possible.

The current implementation keeps the partitioning logic separate from the FL training algorithm so it can be reused for both image and tabular datasets later on.

7. FedAvg implementation

FedAvg is implemented from first principles. It follows the standard server-client training loop introduced by McMahan et al. in the original FedAvg paper.

FedAvg formula

w_{t+1} = sum_{k in S_t} (n_k / sum_{j in S_t} n_j) * w_{t+1}^{k}

This means that the updated global model is the weighted average of the participating clients’ trained models, where the weight is proportional to each client’s local dataset size.

Training flow

  1. The server selects participating clients
  2. The current global model is copied to each selected client
  3. Each client trains locally for a number of epochs
  4. Clients send updated model parameters and sample counts to the server
  5. The server aggregates weights using sample-size weighting
  6. The global model is replaced with the aggregated model
  7. Validation metrics are computed
  8. The round metrics are logged for analysis

The aggregation logic is done in federated_learning/federated/aggregation.py, and it correctly handles floating-point tensors while leaving non-floating-point buffers unchanged.

8. Client and server logic

The project simulates clients on a single machine. This is appropriate for the initial baseline because the goal is to test the learning algorithm, not to build a real distributed deployment yet.

Client behavior

  • Receives a copy of the global model
  • Trains using local data
  • Returns updated parameters and local sample count

Server behavior

  • Chooses subset of clients each round
  • Aggregates client updates
  • Evaluates the updated global model
  • Logs performance and communication statistics

9. Evaluation metrics and logging

Every federated round logs:

  • communication round
  • selected client IDs
  • training loss
  • validation loss
  • validation accuracy
  • macro F1-score
  • AUROC where available
  • training time per round
  • communication volume estimate

These are saved to JSON and CSV files in each experiment folder. This makes it easier to compare runs over time and build research graphs.

After federated training is complete, the final global model is evaluated once on the untouched PathMNIST test split. Results are written to federated_test_metrics.json and stored under federated_test in comparison_summary.json. Per-round validation metrics remain separate; use validation metrics for model selection and test metrics for final reporting.

10. Output graphs and experiment comparison

The framework produces several useful plots, including:

11. IDS dataset interface

Although the exact IDS dataset is not yet provided, the framework already includes a dataset-independent interface so that later integration does not require rewriting the training algorithm. 

class IDSDataInterface:
    def __init__(self, dataset_path, target_column, categorical_columns=None, numeric_columns=None):
        ...

The interface supports:

  • numeric and categorical features
  • train-only preprocessing
  • binary or multiclass labels
  • IID and non-IID partitioning
  • future tabular model training
The IDS dataset should be integrated only after the dataset schema is known, including the target column, categorical features, and preprocessing rules.

12. Reproducibility

Experiments are reproducible through the seed parameter. Each run creates a unique output directory under results/ so results remain traceable and comparable. 

python main.py --dataset pathmnist --num_clients 5 --distribution iid --seed 42 --rounds 20

This is essential for research because identical settings should generate consistent experiment logs and evaluation curves.

13. Security architecture preparation

The baseline contains no security mechanism because the project is intentionally focused on a clean, measurable learning baseline first. However, the architecture is designed so that security layers can be added later without rewriting the main training pipeline.

  • Secure aggregation: replace the current server aggregation function with cryptographic or secure averaging
  • Differential privacy: add noise or clipping in client updates
  • Gradient clipping: constrain client gradients during local training
  • Robust aggregation: median, trimmed mean, or Krum-style aggregation
  • Model poisoning experiments: inject malicious client updates
  • Communication encryption: protect client-server transfer of model parameters

14. How to run the framework

Install dependencies

python -m pip install -r requirements.txt

Run a smoke test

python main.py --dataset pathmnist --smoke_test --num_clients 2 --rounds 1 --local_epochs 1 --batch_size 16 --lr 0.01 --distribution iid

Run a full experiment

python main.py --dataset pathmnist --num_clients 5 --rounds 20 --local_epochs 2 --batch_size 64 --lr 0.01 --distribution iid

Run a non-IID experiment

python main.py --dataset pathmnist --num_clients 10 --rounds 50 --local_epochs 5 --batch_size 32 --lr 0.001 --distribution non_iid --dirichlet_alpha 0.5

15. Summary

This project gives you a clean, modular, and reproducible baseline for federated learning using PyTorch. It is intentionally simple, explains the core FedAvg algorithm clearly, and is prepared for future research on security, privacy, IDS integration, and broader experimentation.

The implementation is ready for PathMNIST baseline experiments and configurable FedAvg simulations, with a future-ready architecture for IDS and security research.
